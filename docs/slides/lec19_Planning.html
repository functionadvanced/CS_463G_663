A Planning Task

Planning finds an action sequence from an initial state (starting arrangement) to a goal (required final conditions).

Can we put A onto B immediately? What must happen first?

C blocks A. A plan must first make A movable.

Use this one arrangement throughout Lectures 19 and 20. A is teal, B gold, C rose. We model a move as a complete transfer of one block, with no separate pickup or hand state. Ask for a proposed sequence before introducing formal notation.

Classical Planning Assumptions

Our planner uses a deliberately simplified model:

Assumption Meaning in this example
Fully observable The current arrangement is known
Deterministic A legal move has one predicted result
Static environment Blocks stay put unless the agent moves them
Finite, discrete states Finitely many distinct arrangements, described by true/false facts
Sequential actions One complete move at a time

A classical plan is a fixed action sequence. Unexpected outcomes may require replanning: computing a new plan from the observed state.

These assumptions describe classical planning, not every planning method. We also ignore action duration and use one unit of cost per move. Real robot control would need geometric feasibility, perception, grasping, and failure handling, which are outside this symbolic model.

[Sources] - AIMA fourth edition, Section 11.1. [/Sources]

Action Schemas and Ground Actions

Objects are named things in the problem: blocks A,B,C and \text{Table}.

An action schema is a reusable action description. A template means it has variables as placeholders, like blanks in a form.

Form Example Meaning
Action schema \text{Move}(b,\text{src},\text{dst}) Move block b from source \text{src} onto destination \text{dst}
Ground action \text{Move}(B,\text{Table},C) Move B from the table onto C

Grounding fills the placeholders: b=B, \text{src}=\text{Table}, \text{dst}=C.

A ground action has specific objects in every slot, with no variables left. The schema also defines when the action is allowed and what it changes.

Planning searches over states. Each legal ground action supplies one edge. The chosen objects must still meet the action’s requirements.

An object is an individual named entity in the domain, not necessarily a Python object. Here B and C name particular blocks, and Table names their shared support. The lower-case b and the descriptive names src and dst are variables to replace, not extra objects.

The full action schema includes preconditions and effects, introduced on later slides. Grounding substitutes the chosen objects throughout those rules as well as in the action’s name. For example, Clear(b) becomes Clear(B). Ground means variable-free, not a physical location or a move onto the ground.

Move(B,Table,C) is applicable in the initial arrangement because B is on the table and B and C are clear. Move(A,Table,B) is also ground, but is initially inapplicable because C blocks A. Grounding and checking applicability are different steps.

This connects planning to the earlier search lectures: a node represents a world state, an applicable ground action supplies an edge to Result(s,a), the goal test checks the required facts, and a solution is an executable action sequence.

Blocks-World Vocabulary

A constant names one object: A,B,C or \text{Table}. A predicate describes a property or relation, such as \text{Clear} or \text{On}.

Fact Meaning
\text{Block}(A) A has type (object category) block; this never changes
\text{On}(C,A) C rests directly on A
\text{On}(B,\text{Table}) B rests on the table
\text{Clear}(B) No block is on top of B

For blocks, Clear means an empty top. \text{Clear}(\text{Table}) is a special, always-true convention: the table can accept several blocks.

We follow AIMA’s two-schema model, which includes Clear(Table). It does not mean that the table has no blocks. A move’s destination must be a block, so Move never deletes Clear(Table). MoveToTable handles the table destination separately.

On and Clear can change. Block facts and the Clear(Table) convention stay fixed. The diagrams show only block arrangements, not every predicate.

The Complete Initial State

A state s is the set of facts currently true in the world.

Where blocks rest:

\begin{aligned} &\text{On}(A,\text{Table}),\quad\text{On}(B,\text{Table}),\\ &\text{On}(C,A). \end{aligned}

Clear facts: \text{Clear}(B),\text{Clear}(C).

Fixed facts: \text{Block}(A),\text{Block}(B),\text{Block}(C) and \text{Clear}(\text{Table}).

Closed-world assumption: facts absent from this complete state are false. In particular, \text{Clear}(A)=\text{false}.

A state is a set of true ground atoms. All the listed facts must hold together, so commas in a set are interpreted conjunctively. Supplying the Clear facts is essential: a planner cannot infer them unless we implement a separate derivation rule.

Contrast with Lecture 17’s logical KB, where an unreported fact could be undetermined. Here the state description is complete under the closed-world convention. This is a modeling assumption, not a rule that missing sensor data proves a physical claim false.

A Partial Goal

A partial goal specifies only the facts we require at the end.

G=\{\text{On}(A,B),\ \text{On}(B,C)\}

The symbol G names the set of required goal facts.

Required Left unspecified by G
A directly on B What C rests on
B directly on C Other facts and additional objects

The goal test G\subseteq s means every fact in G is in state s. Extra true facts are allowed. Both required facts must hold together.

In this exact three-block, acyclic physical domain, C must be on the table in a valid final arrangement. The formula itself does not state this: the domain constraints supply it. With additional blocks, C could rest on another block. Avoid claiming several valid three-block final arrangements for this particular goal.

Preconditions and Effects

Preconditions say when an action is allowed. Effects say what it changes.

Set Role
\text{Pre}(a), or PRE Preconditions: facts required before action a
\text{Add}(a), or ADD Add effects: facts made true
\text{Del}(a), or DELETE Delete effects: facts removed, hence made false

An action is applicable (executable now) when \text{Pre}(a)\subseteq s. Its next state is:

\text{Result}(s,a)=\bigl(s\setminus\text{Del}(a)\bigr)\cup\text{Add}(a).

Here \setminus removes facts and \cup combines fact sets.

The frame problem asks how to represent unchanged facts. Facts outside the effect sets persist: moving C leaves \text{On}(B,\text{Table}) true.

Explain set difference as remove and union as add. The basic fragment used here has positive preconditions and disjoint add/delete lists. Negative effects are entries in the delete list, not negated atoms stored in a state. This is the STRIPS style of representation, named for Stanford Research Institute Problem Solver, with typing and inequality constraints on schema instances.

[Sources] - AIMA Section 11.1, action applicability and the state transition function. [/Sources]

Maintaining the Clear Facts

For a block b, \text{Clear}(b) means no block x rests on b:

\neg\exists x\,\text{On}(x,b).

We store this summary as a fact and update it after each move.

A move changes… Clear fact to update
The old supporting block loses its top block Add \text{Clear}(\text{src})
The destination block gains a top block Delete \text{Clear}(\text{dst})
The moving block’s own top Nothing: it remains clear

The initial state and action effects must keep these summary facts consistent with the arrangement.

The quantified formula explains the meaning for block arguments only. It is not a formula evaluated by the state-set engine. Clear(Table) has the separate capacity convention already stated. Adding Clear(Table) after moving a block off it is harmless because that atom was already true.

[Sources] - AIMA Section 11.1, blocks-world Clear predicate. [/Sources]

Moving Onto a Block

b and \text{dst} are distinct blocks. \text{src} is a block or Table, different from both.

Move(b, src, dst)
PRE: On(b, src) and Clear(b) and Clear(dst)
ADD: On(b, dst), Clear(src)
DELETE: On(b, src), Clear(dst)

Example: \text{Move}(B,\text{Table},C) puts B onto C.

Why must the schema delete \text{Clear}(C)?

B now occupies C’s top. Leaving \text{Clear}(C) true would allow an impossible second block to move onto C.

PRE, ADD, and DELETE refer to the three sets just defined. Type and inequality guards in the sentence above the code are part of the schema, even though we omit their fixed predicates from the displayed PRE line. dst cannot be Table. src may be Table, in which case its Clear atom stays true.

[Sources] - AIMA Figure 11.4, with explicit parameter restrictions and add/delete presentation. [/Sources]

Moving Onto the Table

b and \text{src} are distinct blocks. The table is a constant, not a block.

MoveToTable(b, src)
PRE: On(b, src) and Clear(b)
ADD: On(b, Table), Clear(src)
DELETE: On(b, src)

No occupied-top check or delete effect is needed for the table. It has space for multiple blocks in this model.

This action moves onto the table. Its source must be a block, which excludes the useless MoveToTable(b,Table) instance. The earlier Beamer source mislabeled this as handling moves off the table. Explain the direction from the actual arguments rather than preserving that wording.

[Sources] - AIMA Figure 11.4, MoveToTable action. [/Sources]

Grounding an Action

Use the same replacements in every rule: b=C and \text{src}=A.

\text{MoveToTable}(b,\text{src})\quad\leadsto\quad\text{MoveToTable}(C,A).

Grounded set Facts
Preconditions \text{On}(C,A),\ \text{Clear}(C)
Add \text{On}(C,\text{Table}),\ \text{Clear}(A)
Delete \text{On}(C,A)

The object restrictions also hold: C and A are different blocks.

After this action, does B remain on the table?

Yes. \text{On}(B,\text{Table}) appears in neither effect set, so it persists.

The leadsto arrow denotes schema instantiation, not logical implication. All dynamic preconditions are true initially. The effect both clears A and keeps C’s own top clear.

[Sources] - AIMA Section 11.1. Worked instance of Figure 11.4. [/Sources]

A Plan, Step by Step

Goal: \text{On}(A,B)\land\text{On}(B,C).

1. \text{MoveToTable}(C,A) adds \text{Clear}(A).

2. \text{Move}(B,\text{Table},C) achieves \text{On}(B,C).

3. \text{Move}(A,\text{Table},B) achieves \text{On}(A,B).

At each reveal, ask whether the next move is applicable. Before step 2, C and B are clear. After step 2, B remains clear while C is not. Before step 3, A and B are clear. The two goal facts now hold together.

Checking a Proposed Plan

For k actions a_1,\ldots,a_k, s_i is the state after action i:

  1. Start with the complete initial state s_0.
  2. Check \text{Pre}(a_i)\subseteq s_{i-1} before every action.
  3. Compute s_i=(s_{i-1}\setminus\text{Del}(a_i))\cup\text{Add}(a_i).
  4. Check G\subseteq s_k at the end.

What is wrong with starting our plan with \text{Move}(A,\text{Table},B)?

The action needs \text{Clear}(A), which is false initially. Achieving a goal fact is insufficient if the action is not executable.

Define i as the action index and k as the sequence length. s_i denotes the state after i actions. A validator can reject a plan at the first failed precondition without running a physical robot. It validates the encoded model, so model accuracy still matters.

Effect-Set Practice

Suppose all three blocks are separate on the table. Execute \text{Move}(B,\text{Table},C).

Which facts change? Is B still clear afterward?

Add: \text{On}(B,C),\ \text{Clear}(\text{Table}).

Delete: \text{On}(B,\text{Table}),\ \text{Clear}(C).

\text{Clear}(B) persists. Adding \text{Clear}(\text{Table}) is redundant because that fixed fact already holds.

This is the middle action of the plan. Ask students to distinguish the moving block’s top from the destination block’s top. The effect set is the schema’s specification, while the set of actually changed truth values omits the redundant Clear(Table) addition.

Candidate Actions and Applicability

A candidate is a ground action allowed by the object rules: correct types and different objects where required.

With five blocks and one table:

Schema Parameter choices Candidates
\text{Move}(b,\text{src},\text{dst}) 5 moving blocks, 4 destinations, 4 sources 5\times4\times4=80
\text{MoveToTable}(b,\text{src}) 5 moving blocks, 4 block sources 5\times4=20
Total Before state-dependent checks 100

For example, \text{Move}(A,\text{Table},B) is a candidate but initially cannot run: A is not clear. Candidates still need state-dependent precondition checks.

For Move, choose distinct b and dst among the five blocks. src can be any of the six objects except b and dst, giving four choices. For MoveToTable, src must be one of the four other blocks. Blind enumeration over all six objects would yield 216 plus 36 assignments, but many violate fixed type and inequality guards. We count the well-formed candidates here, not the branching factor of a particular state.

State Growth and Model Constraints

Each Boolean fact is true or false. A truth assignment chooses these values for all m facts, giving up to 2^m combinations.

A state constraint is a rule for a valid arrangement:

  • Each block has exactly one support.
  • A block supports at most one block.
  • No cycles: A on B and B on A is forbidden.
  • Clear facts agree with the arrangement.

An invariant is a rule preserved by every legal action. Our schemas preserve these constraints if the initial arrangement is valid.

m counts dynamic atoms, not objects. For three blocks there are nine possible On atoms and three Clear atoms, yielding 4096 raw assignments, but only 13 valid arrangements in this simplified domain. The Block atoms and Clear(Table) are fixed. We do not need a complexity-class detour to explain why representation and pruning matter.

The schemas preserve the stated invariants from valid states because they move only a clear block onto a clear distinct block or the table. They do not repair an already inconsistent input state. A validator should check the model’s initial state too.

Takeaways

  • A plan must satisfy every action’s preconditions in sequence.
  • Grounding fills a schema’s variable slots with named objects.
  • Add/delete effects update a complete state. Other facts persist.
  • A partial goal tests only its required facts.
  • Type restrictions and state constraints remove invalid candidates.
