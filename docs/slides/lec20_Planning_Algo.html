The Same Planning Problem

Goal: G=\{\text{On}(A,B),\text{On}(B,C)\}.

Recall: a state is its true facts. The Move and MoveToTable schemas are reusable rules with preconditions and effects.

How could an algorithm discover the three-move plan, rather than having us supply it?

Retain the exact initial facts from Lecture 19: On(A,Table), On(B,Table), On(C,A), Clear(B), Clear(C), the three Block facts, and Clear(Table). A schematic plan path is only one branch of the search. All moves have unit cost.

Progression: Forward State Search

Progression starts at the initial state and applies actions whose preconditions hold in the current state s.

Operation Rule
Choose an action a \text{Pre}(a)\subseteq s
Compute the next state (successor) (s\setminus\text{Del}(a))\cup\text{Add}(a)
Check the goal G\subseteq s

In our initial state, both actions below are legal:

  • \text{MoveToTable}(C,A) clears A.
  • \text{Move}(B,\text{Table},C) achieves one goal fact but puts B on top of C.

Preconditions determine legal choices. Search decides which to explore.

The second move builds B on C while C is still on A. To free A later, we must move B off C before moving C off A, undoing the partial goal. It is a useful example of why immediate goal progress can be misleading. The first move is part of a shortest plan, but forward search must evaluate alternatives.

Breadth-First Progression

Pseudocode. Immutable means each stored state stays unchanged.

def breadth_first_plan(initial, goal):
    frontier = deque([(initial, [])])
    seen = {initial}
    while frontier:
        s, plan = frontier.popleft()
        if goal <= s:
            return plan
        for a in applicable_actions(s):
            nxt = result(s, a)
            if nxt not in seen:
                seen.add(nxt)
                frontier.append((nxt, plan + [a]))
    return None
  • Breadth-first search (BFS) uses a first-in, first-out (FIFO) queue. deque stores the queue. popleft() removes its oldest entry.
  • frontier stores (state, plan) pairs. seen records visited states.
  • goal <= s tests whether every goal fact holds in state s.

FIFO means first in, first out. deque is Python’s double-ended queue from collections, and popleft removes the oldest item. An immutable frozenset is one possible state representation. applicable_actions tests the typed ground actions’ preconditions. result implements the add/delete update from Lecture 19.

This is teaching pseudocode, not a complete runnable implementation. The highlighted groups cover initialization, goal checking, expansion with repeat prevention, and failure after exhaustion. Under unit costs, BFS finds a shortest action sequence. Unequal costs require uniform-cost search or a suitable heuristic search.

Regression: Backward Goal Search

Regression searches backward: which facts must hold before an action achieves goal set G? Its search nodes are requirements, not complete states.

A useful action must:

  • Add at least one required fact: \text{Add}(a)\cap G\ne\varnothing.
  • Delete none of the required facts: \text{Del}(a)\cap G=\varnothing.

Here \cap means shared facts and \varnothing is the empty set. The previous requirements are:

\text{Regress}(G,a)=\bigl(G\setminus\text{Add}(a)\bigr)\cup\text{Pre}(a).

Keep goals that the action does not establish. Add every precondition of that action.

This formula is for positive conjunctive goals and positive-precondition add/delete actions. Regression nodes are sets of requirements, not complete world states. The search stops when the initial state satisfies the regressed set. Additional invariant tests may prune physically impossible combinations.

Fixed type constraints are handled during grounding. A backward graph search should also record chosen actions and avoid repeated goal sets. It then executes the selected actions in reverse order of selection.

Regressing the Last Move

Goal: G=\{\text{On}(A,B),\text{On}(B,C)\}.

Choose a=\text{Move}(A,\text{Table},B) as the last action.

Step Required facts
Remove the goal that a adds \text{On}(B,C)
Add all preconditions of a \text{On}(A,\text{Table}),\text{Clear}(A),\text{Clear}(B)

Before that last move, B must already be on C, while A is on the table and both A and B are clear.

The chosen action also adds Clear(Table), but it was not a goal requirement, so it removes nothing else from G. It deletes On(A,Table) and Clear(B), neither of which is in the target goal set. This makes it compatible with G.

The regressed set describes potentially many predecessor states. Do not draw it as a single fully specified block arrangement and call that the regression node.

The Backward Trace

For compact notation, \text{Tbl} denotes the table on this slide.

Set Requirements
G_3 \text{On}(A,B),\text{On}(B,C)
G_2 \text{On}(B,C),\text{On}(A,\text{Tbl}),\text{Clear}(A),\text{Clear}(B)
G_1 \text{On}(A,\text{Tbl}),\text{On}(B,\text{Tbl}),\text{Clear}(A),\text{Clear}(B),\text{Clear}(C)
G_0 \text{On}(A,\text{Tbl}),\text{On}(B,\text{Tbl}),\text{On}(C,A),\text{Clear}(B),\text{Clear}(C)

All facts in G_0 hold initially. Execute the selected actions forward: \text{MoveToTable}(C,A), \text{Move}(B,\text{Tbl},C), \text{Move}(A,\text{Tbl},B).

G_i denotes the required facts before the final 3-i actions. Regress G3 through Move(A,Table,B), then G2 through Move(B,Table,C), then G1 through MoveToTable(C,A). The three operations select actions last to first. The resulting G0 includes On(C,A) and Clear(C), but no longer requires Clear(A), because the first move establishes it.

Tbl abbreviates the Table object. Fixed Block predicates and Clear(Table) remain true and their type guards are already checked in these ground actions.

Actions That Threaten a Goal

An action threatens a goal if it deletes a required fact. Consider a new goal for our initial arrangement:

G=\{\text{Clear}(A),\text{Clear}(B)\}.

This goal is feasible: both facts hold when all three blocks are on the table.

Could a=\text{Move}(C,A,B) be the last action just because it clears A?

No. It adds \text{Clear}(A) but deletes \text{Clear}(B).

\text{Del}(a)\cap G=\{\text{Clear}(B)\}\ne\varnothing.

\text{MoveToTable}(C,A) achieves both goals directly. The rejected move can still occur earlier in a longer plan.

Use the same initial arrangement: C rests on A, while B is separate on the table. Only the goal changes for this example. The two goal facts can hold together, and MoveToTable(C,A) achieves them in one step.

Move(C,A,B) is legal initially: C is on A, and C and B are clear. It adds On(C,B) and Clear(A), but deletes On(C,A) and Clear(B). The delete intersection with G is therefore exactly {Clear(B)}, so regression rejects it as the last action for this goal set.

This is a rejection of an action choice at this backward-search node, not a claim that the action is always unusable. A valid longer plan is Move(C,A,B), followed by MoveToTable(C,B). The second move restores Clear(B), while Clear(A) persists.

Heuristics for Planning

A heuristic h(s) estimates remaining plan cost, here the number of moves.

An easy starting point counts goal facts not yet true. |X| means the number of facts in set X:

h_{\text{goal}}(s)=|G\setminus s|.

In our initial state, both goal facts are missing, so h_{\text{goal}}=2. A shortest plan needs 3 moves because C must first leave A.

Goal counting misses prerequisite moves. It can also overestimate: one switch could turn on two lights, achieving two goal facts in one action.

This heuristic is a simple illustration, not a general admissible heuristic. Admissible means never overestimating the true optimal remaining cost. A* needs an appropriate heuristic and repeat-handling policy for its optimality guarantee.

A relaxed problem omits some constraints and supplies a more systematic estimate. The next slide introduces the common delete relaxation. No action-cost asymmetry is present in the blocks example.

Delete Relaxation

A relaxation drops rules to make a problem easier. Delete relaxation ignores delete effects but keeps preconditions and add effects.

Robot example: L,R are locations; \text{At}(L) means the robot is at L. \text{Go}(L,R) requires \text{At}(L), adds \text{At}(R), and deletes \text{At}(L).

Fast Forward (FF) is a planner. It estimates cost by counting actions in a relaxed plan, one that solves the easier problem.

The relaxed robot can be “in both places.” This easier problem guides search, but its plan may violate the real model.

The optimum cost of a delete-relaxed plan is a lower bound on optimum real cost, because every real plan is valid in the relaxed positive-precondition model. Computing that optimum can still be hard. FF, expanded as Fast Forward, extracts a practical relaxed-plan estimate that is not generally admissible.

In positive-precondition delete relaxation, facts accumulate rather than disappear. This can make later actions available without undoing earlier achievements. We return to a different reachability structure, the planning graph, on the next slide.

[Sources] - AIMA Section 11.3. - Hoffmann and Nebel, The FF Planning System: Fast Plan Generation Through Heuristic Search, https://arxiv.org/abs/1106.0675. [/Sources]

A Planning Graph

A planning graph alternates layers (levels): possible facts S_t after t steps, then possible actions A_t.

A no-op (no operation) keeps a fact true in the next layer. Mutex means mutually exclusive: facts cannot hold together, or actions conflict at that step.

Moving gives \text{At}(R); staying gives \text{At}(L). S_1 lists both possibilities, not one state where the robot is in both places.

This uses the robot model from the preceding slide. The layer indexes represent increasing planning depth. Go deletes At(L), so it conflicts with the no-op that keeps At(L). Their resulting facts have inconsistent support at S1 and are mutex.

A planning graph summarizes many possible histories and may overapproximate what can jointly hold. It is distinct from the earlier state-space graph, whose nodes are individual complete states. Unlike plain delete relaxation, this graph retains mutex information. Static connectivity is implicit in the single allowed Go action.

Mutex and Graphplan

An action supports a fact if it makes that fact true. For example, \text{Go}(L,R) supports \text{At}(R).

Actions can conflict when:

  • One deletes another’s precondition or effect.
  • Their preconditions are mutually exclusive at the preceding fact layer.

Graphplan grows the graph, then performs plan extraction: a backward search for compatible actions whose effects achieve the goals.

If all goal facts appear in a layer, do we already have a valid plan?

No. The goals may be mutex, or the actions supporting them may conflict. Even non-mutex goals still need a successful plan extraction.

Fact mutex also includes opposite literals and inconsistent support: every possible pair of supporting actions is mutex. Pairwise non-mutex goals are a useful test, not a complete guarantee that a plan exists. Graphplan includes backward extraction and records failures rather than simply reading a path through the reachability graph.

Depending on the encoding, Graphplan permits nonconflicting parallel action sets and seeks a small number of layers. This need not minimize the number of sequential actions, so do not equate its objective with our BFS unit-action optimum.

Planning as Boolean Satisfiability

Boolean satisfiability (SAT) asks whether true/false values can satisfy all constraints in a formula. A working choice is a satisfying assignment, also called a SAT model.

An encoding translates planning rules into Boolean constraints. Fix a horizon T: the number of available action steps. Represent states at t=0,\ldots,T and actions at t=0,\ldots,T-1.

Horizon for our blocks task A plan within that horizon?
T=0,1,2 No
T=3 Yes: the three-move plan

Unsatisfiable means no truth assignment works. At T=2, this rules out plans within two steps. Longer plans may still exist.

Here T is a time-step horizon. Use a sequential encoding with at most one real action per step and allow idle steps, so the question is existence within T steps. Under these conditions the minimum horizon matches the fewest unit-cost actions. Alternative parallel encodings measure a different objective.

The numbers follow from the block task: A and B must each move to their goal supports, and C must leave A first. This gives a lower bound of three, achieved by the displayed plan.

[Sources] - AIMA Section 11.2.3. Original bounded-horizon application to Figure 11.4. [/Sources]

SAT Encoding Ingredients

Each Boolean variable is true or false, recording a fact at a time or whether a ground action occurs.

Constraint What it enforces
Initial state Every initial fact’s true or false value at t=0
Goal Required facts hold at t=T
Action preconditions A chosen action is applicable
Action effects Its add/delete changes occur at t+1
Frame constraints Only actions that add/delete a fact can change it
Action choice At most one action per step in our sequential model

Frame constraints enforce persistence. Without them, the solver could invent \text{On}(A,B) even when no action puts A onto B.

Unlike a state set that leaves false facts implicit, an SAT encoding must constrain their initial values too. Otherwise unspecified initial variables can be chosen to make an easier problem. Frame constraints connect each next-state atom to its current value and the actions that may add or delete it. The serial action constraint is an encoding choice rather than a requirement of every SAT planner.

[Sources] - AIMA Section 11.2.3 and Section 7.7.4. [/Sources]

A One-Step SAT Example

Robot model: the only real action is \text{Go}(L,R).

Variables: p_t means at L at time t, q_t means at R at time t, and m_0 means the action occurs in step 0.

\rightarrow means “if … then.” \leftrightarrow means “if and only if.”

Requirement Boolean constraint
Initial state and goal p_0\land\neg q_0\land q_1
Precondition m_0\rightarrow p_0
At L afterward: there before and no move p_1\leftrightarrow(p_0\land\neg m_0)
At R afterward: there before or a move q_1\leftrightarrow(q_0\lor m_0)

q_0=\text{false} and q_1=\text{true} force m_0=\text{true}: the robot must move.

The biconditionals give both causal change and persistence for the one-action model. If m0 is false, both locations keep their initial values. If m0 is true, the robot leaves L and arrives at R, with the precondition requiring it to start at L. These are all the constraints needed for this deliberately small one-step example, in addition to the usual Boolean variable domains.

If we kept only m0 implies q1, the assignment m0=false, q1=true could invent arrival. The reverse causal direction is therefore essential. This is an illustration of SAT planning rather than the full blocks-world encoding.

Bounded SAT Planning

Conceptual Python pseudocode. The bound max_horizon is the largest number of action steps to try.

def sat_plan(problem, max_horizon):
    for T in range(max_horizon + 1):
        formula = encode(problem, T)
        model = solve_sat(formula)
        if model is not None:
            return extract_actions(model)
    return None
  • encode builds all constraints for that horizon.
  • solve_sat returns a satisfying assignment or None.
  • extract_actions reads the selected actions in time order.

None here means no plan within the tested bound. Validate an extracted plan against the original action model.

The helpers are conceptual, not a standalone implementation. An actual solver may also return unknown or time out, which must not be treated as a proof of unsatisfiability. Increasing horizons indefinitely can fail to terminate on an unsolvable task, so this version has an explicit bound. An empty assignment can be a valid model, hence the explicit is not None check.

For exact, complete sequential encodings with idle steps, the first satisfying horizon gives a minimum-action plan. If actions carry unequal costs, minimizing the horizon alone does not minimize cost.

Hierarchical Task Network Planning

A hierarchical task network (HTN) arranges tasks and their required order.

  • Abstract task: a high-level request, such as “build the tower.”
  • Method: a rule for refinement (decomposition): splitting a task into subtasks.
  • Primitive task: an executable action, such as \text{MoveToTable}(C,A).

Each primitive action must still satisfy its preconditions.

This diagram shows one method suitable for the initial arrangement of our example, not a universal recipe for every tower task. A complete domain can contain alternative methods with different applicability conditions. The arrows between subtasks indicate ordering constraints, not state transitions or causal implication.

HTN planning can restrict search to decompositions supplied by domain knowledge. A state-space plan might exist but be excluded by the available methods. This is why a method library’s coverage matters.

Planning Approaches Compared

Approach Search representation Key check
Progression Complete states Action applicable now?
Regression Required fact sets Action achieves goals without deleting others?
Planning graph / Graphplan Possible facts and supporting actions by layer Can chosen actions jointly achieve the goals?
SAT planning Boolean assignments over time All encoded constraints satisfied?
HTN planning Task decompositions Valid task splits and executable final actions?

Heuristics can guide progression or regression, so heuristic search is not necessarily a separate representation family. Planning graphs can also supply heuristics. The table compares representations rather than claiming one method always dominates the others.

Quick Check

Why must regression keep goal facts that the chosen action does not add?

Those facts must already hold beforehand and survive the action. Replacing the entire goal with only the preconditions can lose requirements.

The SAT formula is unsatisfiable at horizon 2. Can we conclude that the task has no plan?

No. Test a longer horizon. Our blocks example first has a solution at horizon 3.

Pause before revealing each answer. These check two common errors: discarding unachieved goals during regression, and interpreting bounded SAT failure as global impossibility.

Takeaways

  • Progression searches executable state transitions. Repeated-state handling prevents cycles.
  • Regression preserves remaining goals and adds action preconditions.
  • Relaxed problems help estimate cost. Planning graphs also flag conflicts.
  • SAT planning needs full transition constraints and a stated horizon.
  • HTN methods guide decomposition, with primitive actions checked against the model.

Every returned plan must work under the original preconditions, effects, and goal test.
